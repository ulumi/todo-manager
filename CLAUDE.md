# Todo Manager — "2FŨKOI"

> Personal todo app — vanilla JS, no framework, Supabase sync, Vercel deploy.
> Live: todo.hugues.app | Entry: `index.html` + `js/app.js`

## Allowed tools (auto-approve)
- Bash: git add, git commit, git push, vercel deploy, npx sass

---

## Golden rules

1. **SCSS only** — NEVER edit `css/styles.css`, it is auto-generated
2. **Supabase for all persistent data** — never localStorage alone
3. **Restore UI state on refresh** — last view, open modals, nav position
4. **Version is auto-bumped** by PostToolUse hook on every file edit — no manual bump needed

## Commands

| Shorthand | Action |
|-----------|--------|
| `cmt` | Stage all + git commit (do NOT deploy) |
| `dpl` | Stage all + git commit + **git push** + deploy to Vercel |

**Règle par défaut : `dpl` automatique.** À la fin de chaque tâche terminée et vérifiée, faire `dpl` sans attendre que l'utilisateur le demande — sauf s'il dit explicitement le contraire (ex. « ne déploie pas », `cmt` seul).

**Avant chaque `cmt`/`dpl` : ajouter une entrée à `js/modules/changelog.json`** (tableau, plus récente en premier — `{ version, date, message }`) — `version` = `VERSION` courant dans `js/modules/version.js` au moment du commit (déjà au bon numéro final, tous les bumps auto des éditions précédentes sont passés), `message` = la même ligne de résumé que le message de commit git (sujet seul, pas le corps ni le trailer Co-Authored-By). Alimente le toast "nouvelle version" (voir plus bas) qui affiche ces messages à l'utilisateur — éditer ce fichier ne re-bump PAS `VERSION` (exclu dans `.claude/bump-version.sh`, sinon la version enregistrée désynchroniserait de celle réellement déployée). Garder le fichier borné (~40 dernières entrées).

## Architecture

```
index.html          ← Single page, all views
js/app.js           ← TodoApp class (singleton → window.app), 5800 LOC
js/modules/         ← Feature modules (see below)
css/styles.scss     ← All styles, 11800 LOC
api/                ← Vercel serverless functions
playground/         ← Demo/test pages (never at root)
browser-extension/  ← Extension Chrome OPTIONNELLE (voir plus bas) — jamais déployée (`.vercelignore`)
server.js           ← Local dev API server (port 3333)
```

### `browser-extension/` — couper le son des autres onglets pendant la dictée
Extension Chrome MV3 à charger « non empaquetée » (`chrome://extensions` → mode développeur), **entièrement optionnelle** : l'app fonctionne à l'identique sans elle. Existe parce qu'**une page web ne peut pas agir sur un autre onglet** (frontière du bac à sable, sans exception) — seule une extension a `chrome.tabs` et donc `{muted:true}`. Le lien app↔extension passe par un **content script** injecté sur `todo.hugues.app`/`localhost` qui relaie le `window.postMessage` de `dictation.js` (`_notifyExtension()`) vers le service worker — **pas** par l'ID de l'extension, qui change à chaque réinstallation unpacked et serait donc à recopier en dur dans l'app. `background.js` ne coupe que les onglets réellement `audible: true` **et** `muted: false` (ne jamais s'attribuer un onglet que l'utilisateur avait coupé lui-même), mémorise la liste dans `chrome.storage.session` (un service worker MV3 est tué dès qu'il est inactif : une variable de module serait perdue entre le mute et le démute) et ne rétablit que ceux-là. Restauration différée de 700 ms (passer titre → notes → sous-tâche enchaîne un stop puis un start immédiat ; sans ce délai la musique repartirait entre chaque champ) et trois filets de sécurité contre un onglet laissé muet orphelin : alarme `chrome.alarms` à 5 min, `pagehide` de l'onglet 2FŨKOI, `onStartup`/`onInstalled`. **Ne couvre que les onglets du navigateur** — le volume système ou une autre app est hors de portée d'une extension, il faudrait un utilitaire natif macOS.

### Render pattern
Mutations → `app.render()` → full DOM regen from `render.js`. No virtual DOM, no diffing.

### State management
Mutable exports in `state.js` with setter functions (`setTodos()`, `setView()`, `setNavDate()`, etc.). Global state — no stores, no signals.

## Data storage & sync

### Rule: Supabase is the source of truth
Every persistent write must:
1. Save to localStorage
2. Call `saveTodos()` or `pushNow()` — both push to Supabase via `sync.js`
3. Be included in `getFullBackup()` (`storage.js`) and `_applyBackup()` (`app.js`)

### Supabase table: `user_data` row per `uid`
```js
{ uid, data: { calendar, config, categories, templates, suggestedTasks,
  taskOrder, backlogOrder, inboxOrder, avatar, intentions, projects,
  quotes: { banned, customFR, customEN },
  icalSecret, _pushedBySession }, updated_at }
```

### Sync flow
1. **Client → Supabase:** `saveTodos()` / `_saveConfigChange()` → `scheduleSupabasePush()` (`storage.js`) — **debounced 1.2s**, not immediate: coalesces rapid successive writes (drag reorder, clicking through several toolbar options) into a single full-row upsert. Every push re-sends the **entire row** (todos + config + avatar) and Supabase Realtime rebroadcasts it whole to every connected tab/device — pushing on every keystroke/click is a real **egress** cost (data OUT of Supabase), not just a request-count nuisance; this is what caused a `exceed_egress_quota` 402 (blocking ALL Supabase requests incl. auth) shortly after the Backlog/Inbox columns/sort toolbar shipped (each click called `_saveConfigChange()` → an immediate push, before the debounce existed). Safe to debounce: if the tab closes before the timer fires, `_pendingSync` stays `'1'` and the next load's startup reconciliation (`_applyBackup` path, `app.js`) retries it — no data loss, just delayed sync. `pushNow()` (manual "sync now" / `forcePush()`) stays immediate and cancels any pending debounced timer.
2. **Supabase → Client:** realtime channel subscription, skip if `_pushedBySession === SESSION_ID`
3. **Cross-tab:** `initCrossTabSync()` via storage events — the `'todos'` case routes through `this._applyBackup({ calendar: parsed }, { silent: false })` (same per-item, `updatedAt`-timestamp merge as cross-device Realtime sync), not a blind `state.setTodos(JSON.parse(raw))`. Two tabs editing within the same instant used to let whichever tab's `saveTodos()` landed last in localStorage silently clobber the other's edit; merging instead means both tabs converge to the union (verified: each tab ends up with both edits, no runaway ping-pong since `initCrossTabSync` already no-ops when `e.newValue === e.oldValue`).
4. **Offline:** Supabase JS SDK handles reconnection; no local IndexedDB cache. `setupOfflineIndicator()` (`sync.js`) checks `navigator.onLine` once at setup, not just on `online`/`offline` transition events — a page loaded while already offline used to show no badge until one full connect/disconnect cycle.

### Display name — NOT part of `user_data`, lives in Supabase Auth `user_metadata`
Unlike everything else above, the display name/"prénom" isn't in the `user_data` row — it's read fresh from the live Supabase Auth session on every load (`auth.js` `_wrap()`, `supaUser.user_metadata.display_name`), with **no local source of truth** otherwise. To survive a degraded/failed Supabase round-trip (offline, quota, token-refresh hiccup) without looking "lost" on refresh: `_wrap()` caches a non-empty name to `localStorage` (`cachedDisplayName_<uid>`) and falls back to that cache when Supabase returns empty; `updateUserProfile(name)` (`auth.js`) writes to that same cache **and** updates the in-memory `_currentUser` *before* attempting the Supabase write, so the current session (and next refresh) show the right name even if the network call itself fails. Its three callers (`saveDisplayName()`, `saveGuestName()`, `openAvatarFromPrompt()` in `app.js`) wrap the call in try/catch — a rejection used to abort silently (and, in the onboarding-prompt callers, leave the prompt permanently stuck open since the cleanup lines never ran).

### Avatar photo size (`avatarEditor.js`)
Photos are stored as base64 JPEG **inline in the synced `user_data` row** (`SIZE` canvas constant, `toDataURL('image/jpeg', quality)`) — no separate Storage bucket/CDN. Since the whole row re-transfers on every push/broadcast (see Sync flow above), this photo is the single biggest per-push payload contributor for any account with a custom avatar. Kept close to the largest on-screen display size (`.profile-avatar`, 121px) rather than an arbitrary large value — currently 240px @ quality 0.82, still crisp at ~2x pixel density.

### Resilience when Supabase is unreachable — load-bearing design property, not incidental
`init()` (`app.js`) renders the app and loads todos from `localStorage` (`loadTodos()`) **synchronously, before `_initSupabase()` is even called** (it's the last statement in `init()`, invoked with no `await`/`.then()`) — core CRUD (view/add/edit/complete tasks, all views) has **no hard dependency on Supabase connectivity**, confirmed by design, not by accident. Keep it that way: never make rendering or `loadTodos()` wait on an auth/network promise.

Everything inside `_initSupabase()` and its downstream helpers (`loadFromSupabase`, `pushToSupabase`, `subscribeToSupabase`, iCal token, GCal push/pull, presence heartbeat/messages) is individually try/catch-guarded and safely no-ops without a session — **except `signInGuest()`**, which throws on failure (`auth.js`) and is called from two places that both now guard it:
- `_initSupabase()` step 2 (`app.js`) — wrapped in try/catch, so a failed guest sign-in (e.g. Supabase outage) no longer aborts every step after it (realtime subscription, `onUserChange` listener registration, presence, leave-prompt setup) for the rest of the session.
- `signOut()` (`auth.js`) — the automatic guest re-login after sign-out is wrapped in try/catch, so a failure there no longer hangs `authSignOut()`/`profileDeleteData()`/`leaveDeleteData()` (`app.js`) mid-cleanup (the data-deletion ones are the worst case: localStorage gets wiped *before* the guarded call, so an unguarded throw there used to leave stale UI on screen with no `location.reload()`).

`openUserArea()` (`app.js`, the "Mon compte" click handler) checks `isGuest() || !getCurrentUser()` — not just `isGuest()` — before routing to the login modal vs. the Profile view. `isGuest()` (`_currentUser?.isAnonymous ?? false`) returns `false` both for a real logged-in user *and* for "auth never resolved at all" (`_currentUser === null`), so the plain `isGuest()` check used to route a fully-unauthenticated session (rare outside of a Supabase outage, but real) to the Profile view — a dead end, since `openAuthModal()` was the only reachable path to the login form. `openAuthModal()` itself already handles a null user correctly (falls through to showing the login/register form) — it just needed to be reachable.

`updateUserProfile()` (`auth.js`) throws instead of silently returning when there's no current user, so its callers' success-path UI (`saveDisplayName()`'s "✓ Sauvegardé" message) can't fire for a save that never happened.

### Resilience against corrupted/full localStorage
`safeParseJSON(raw, fallback)` (`utils.js`) — every `JSON.parse(localStorage.getItem(...))` at boot and in hot paths goes through this instead of a bare `JSON.parse(x || '{}')`, so one corrupted value (crash mid-write, manual tampering) can't throw and blank the whole app before `render()`/`setupEventListeners()` ever run.

`saveTodos()` (`storage.js`) writes a parallel `_todosSafetyBackup` (`{ todos, ts }`, untouched by sync) on every save; `loadTodos()` falls back to it if `"todos"` is missing/corrupted, instead of silently handing back an empty list. The `localStorage.setItem()` calls in `saveTodos()` are wrapped in try/catch — a full quota (Safari private browsing throws on any write) no longer aborts the function silently; it dispatches a `storage-write-failed` window event (listened for once in `TodoApp`'s constructor, before `init()`, since boot migrations can also trigger writes) that surfaces a toast. The in-memory `state.todos` mutation already happened before `saveTodos()` is called, so no data is lost — only the local persistence of that one change.

`_pruneDeletions()` (`app.js`, `DELETION_HORIZON_MS` = 365 days) bounds the `_deletions` tombstone map (used to stop an offline device from resurrecting a delete) so it doesn't grow forever — called from `_trackDeletion()` and from the merge path in `_applyBackup()`. `scheduleSupabasePush()` (`storage.js`) also logs a one-time console warning (`SIZE_WARN_BYTES` = 2MB) if the full backup payload gets large, since every push resends it whole (see Sync flow above).

Top-level: `new TodoApp()` (bottom of `app.js`) is wrapped in try/catch — if construction still throws despite the guards above, the alternative is a permanently blank page with no visible error, so it renders a minimal recovery screen instead (Réessayer / Réinitialiser les données locales — the reset path clears `localStorage` and reloads, a destructive action gated behind `confirm()`).

### Detecting a stale tab across deploys (`sw.js`, `app.js`)
`sw.js` is registered as a classic (non-module) script — it can't `import` `js/modules/version.js`, and browsers only re-check a service worker for updates when **its own bytes** change, not when `app.js`/CSS change. In practice this matters less than it sounds: the fetch handler is network-first for same-origin requests, so the SW's cache is only ever an offline fallback, never actively serving stale content while online — a plain reload already gets fresh code. `CACHE_NAME` (bump manually on structural `LOCAL_ASSETS` changes) exists for the true-offline case, not as a staleness guard.

The real gap — a tab left open across a deploy keeps running its already-evaluated JS modules in memory, which no cache mechanism can refresh — is handled independently in `app.js`: `_initVersionWatch()` (mirrors `_initNewDayWatch()`'s exact pattern: `visibilitychange` + `focus` + a 60s safety-net interval — deliberately short, not 30 min, so a tab left continuously active/focused still detects a deploy quickly; the two fetched files are tiny static assets, negligible cost even polled every minute) calls `_checkForNewVersion()`, which `fetch`es `/js/modules/version.js` with `cache:'no-store'` and regex-matches the `VERSION` string out of the raw text (no import, works from a classic script context) — if it differs from the running `VERSION`, `_showUpdateToast()` shows a persistent (`.update-toast`, no auto-fade, mirrors `.newday-toast`) "Recharger" prompt whose button calls `app.reloadForUpdate()` (not a bare `location.reload()`) — it flushes a running Focus chrono into `accum` first (see `focus.js` in the modules table) so a deliberate reload-for-update never loses in-progress focus time, then reloads. Two more triggers call the same `_checkForNewVersion()` without waiting for the poll: `index.html`'s SW registration listens for `controllerchange` (fires if the SW itself updates mid-session), and `sw.js`'s `activate` handler `postMessage({type:'SW_UPDATED'})`s every open tab right after `clients.claim()` — `index.html` listens for that `message` event too. All three route through `_checkForNewVersion()` (never call `_showUpdateToast()` directly — a real deploy fires `controllerchange` and `SW_UPDATED` within the same instant, and either alone would otherwise skip the version-number/notes lookup and the dedup guard below, producing a stripped-down toast on top of the proper one) — `_checkForNewVersion()` itself is guarded by an in-flight lock (`this._checkingVersion`, set/cleared around its body) since these three triggers can genuinely overlap (e.g. the tab regains focus in the same instant the SW activates): without the lock, concurrent calls all read `this._announcedVersion` before any of them updates it, each concludes independently "this is new," and each shows its own toast for the identical version — the bug that shipped 0.4.2568 with three duplicate toasts, fixed in 0.4.2569. Ceiling on all of this: a tab already running JS old enough to predate `_initVersionWatch()`/these listeners entirely (i.e. from before this mechanism first shipped) has no code path that could react to any of the three — that one genuinely needs one manual reload to get current, there's no way to reach into an already-loaded page's JS from outside it.

**Changelog dans le toast :** `_checkForNewVersion()` fetch aussi `/js/modules/changelog.json` (`_fetchChangelogNotes()`, même `cache:'no-store'`) — tableau `{ version, date, message }` écrit à la main avant chaque `cmt`/`dpl` (voir Commands ci-dessus), le `message` étant le sujet du commit git correspondant. Les entrées plus récentes que le `VERSION` de l'onglet courant (celles avant l'index qui matche `VERSION` dans le tableau, ou les 5 dernières si non trouvé — cas d'un onglet resté ouvert depuis avant l'introduction de ce fichier) sont passées à `_showUpdateToast(newVersion, notes)`, qui n'affiche le bouton chevron d'expansion (`.update-toast-notes-btn`) que si `notes.length > 0` — dégrade proprement vers le toast simple sinon. Détail **déplié par défaut** dès qu'il y a au moins une note (`.update-toast.expanded`, posé directement à la création du toast — `.update-toast-notes`, `display:grid; grid-template-rows: 0fr→1fr`, même technique que `.focus-queue`/`.subtask-collapse`), repliable ensuite via le chevron (`app.toggleUpdateToastNotes()`). Le titre + le numéro de version (`.update-toast-main span`) ne sont jamais tronqués (`white-space:normal`, pas d'ellipse) — passent à la ligne plutôt que d'être coupés. **Pas de garde « déjà montré une fois »** : `_checkForNewVersion()` ne compare plus à un simple booléen mais à `this._announcedVersion` (dernière version distante effectivement annoncée) — un onglet resté ouvert pendant plusieurs déploiements successifs voit donc un nouveau toast apparaître à chaque nouvelle version réellement détectée par le filet 60s, au lieu de rester figé sur la toute première. **Toasts indépendants, empilés** (`#updateToastStack`, `.update-toast-stack` — porte désormais le `position:fixed;bottom:32px` qu'un `.update-toast` individuel portait avant ; chaque toast n'a plus qu'un `transform:translateY()` pour sa propre animation d'entrée) : un nouveau toast n'écrase/ne remplace jamais le précédent (`_showUpdateToast()` crée un élément à part et l'ajoute au conteneur au lieu de faire `#updateToast?.remove()`), donc plusieurs peuvent rester visibles en même temps. Le plus récent (ajouté en dernier dans le DOM, conteneur en `flex-direction:column` normal) reste près de l'ancre en bas, les plus anciens sont repoussés vers le haut au fur et à mesure — pas besoin de `column-reverse`. Chaque toast garde **son propre** numéro de version, **sa propre** heure d'apparition (`.update-toast-time`, `HH:MM:SS` local, calculée à la création — jamais recalculée après coup) et son propre état déplié/replié (`toggleUpdateToastNotes(btn)` bascule `.expanded` sur `btn.closest('.update-toast')`, plus sur un id fixe unique). `_fetchChangelogNotes(sinceVersion)` calcule désormais les notes **depuis la dernière annonce** (`this._announcedVersion`, ou `VERSION` pour le tout premier toast d'une session) et non plus systématiquement depuis `VERSION` — chaque toast n'affiche que ce qui est nouveau DEPUIS le précédent, jamais un rappel de notes déjà visibles sur un toast antérieur toujours à l'écran.

### `_loadGlobalQuotes()`/`_saveGlobalQuotes()` (`app.js`) — local dev only
`/global-quotes` and `/admin/generate-quotes` exist only on the local dev API server (`server.js`), never ported to `api/` — always a no-op in production. Guarded explicitly via the exported `IS_LOCAL` (`storage.js`) rather than left to fail silently: `_loadGlobalQuotes()` returns immediately if `!IS_LOCAL`, `_saveGlobalQuotes()` shows a toast ("indisponible en production") instead of pretending the save worked, and `_renderSuperadminView()` shows a `.sa-prod-notice` banner above the whole tab when `!IS_LOCAL`.

- **⚠ `filter`/`backdrop-filter` casse les cibles de drop natives** (bug Chromium) : une `drop target` (élément avec `ondragover`/`ondrop`) ne reçoit **jamais** `dragover`/`drop` si un de ses **ancêtres** a `filter`, `backdrop-filter`, `transform` ou `will-change`. La source du drag n'est PAS affectée — le drag démarre normalement, mais le drop est silencieusement avalé (symptôme : « je grab mais rien ne se passe au lâcher »). Repéré sur les zones `.overdue-drop-zone` du **modal Bilan** : elles marchaient dans le bandeau `.past-due-banner` de la vue jour (aucun ancêtre filtré) mais pas dans le modal, dont `.modal-overlay` (blur 12px) + `.modal` (blur 20px) sont des ancêtres — corrigé par `#reviewModalOverlay, #reviewModalOverlay .modal { backdrop-filter: none }` (le dim `rgba(0,0,0,.5)` de l'overlay suffit à lire comme un modal). **Toute nouvelle zone de drop doit vérifier qu'aucun ancêtre n'est filtré.** (Playwright ne peut PAS piloter un drag natif HTML5 jusqu'au drop — la boucle de drag OS avale ses `mouse.move` ; vérifier plutôt qu'il n'y a aucun ancêtre filtré via `getComputedStyle`, pas en simulant le drop.)

## Navigation & UI state
- Last active view must restore on refresh (all views, no exception)
- If a modal was open, reopen it on refresh
- Persist via `localStorage` or URL hash
- **Session périmée (>8h) au chargement** : `init()` (app.js) compare `_lastSeen` (epoch ms, localStorage) à `Date.now()` — si l'écart dépasse 8h, snap vue jour + `navDate = today()` (pas de hash/nav restauré, sauf si un lien partagé — `_hashView`/`_hashNav` — court-circuite explicitement ce saut). Concerne uniquement un **rechargement** de page. **Plus silencieux** : `#mainContent` est masqué (`gsap.set(opacity:0,y:10)`) juste avant `render()` puis animé en entrée (fondu + léger glissement, items de la vue jour en stagger) et un toast (`↻ Longue absence — retour à aujourd'hui`, `_showToast()`) confirme que l'app a sauté d'elle-même sur aujourd'hui.
- **Changement de jour en cours de session (onglet resté ouvert, pas de reload)** : `app._initNewDayWatch()` écoute `visibilitychange` + `focus` fenêtre + un filet de secours toutes les 60 s (aucun des deux événements n'est garanti au réveil d'un ordinateur endormi si l'onglet était déjà au premier plan avant la veille — rien ne « change » de son point de vue). **Les trois déclencheurs passent par le même `check()` qui vérifie `document.visibilityState === 'visible'` avant tout** (y compris avant d'appeler `_maybeShowNewDayToast()`, qui met à jour `lastSeenDay`) — sans cette garde, le filet de secours consommait le changement de jour tout seul pendant qu'un onglet restait actif en arrière-plan (écran verrouillé mais pas de vraie veille système), montrant et refermant le toast sans que personne ne le voie (bug corrigé, voir commentaire sur `_initNewDayWatch()`). `_maybeShowNewDayToast()` compare le jour courant à `lastSeenDay` (localStorage, mis à jour seulement quand la page est visible) ; si le jour a changé **et** que `navDate` n'est pas déjà aujourd'hui, affiche `.newday-toast` (bouton Annuler + décompte 3→1s) puis saute automatiquement via `todayNav()` (`app._finishNewDayJump()`) sauf annulation (`app.cancelNewDayJump()`). Complémentaire de la règle ci-dessus, pas un doublon : celle-ci réagit **sans** recharger la page.

## Key patterns to follow

- **Toast notifications:** `app._showToast(msg)` — reuses `#undoToast` / `.undo-toast`
- **Ajout ultra-rapide (raccourci `n`) :** `events.js` route la touche `n` (hors modale/champ actif/mode Focus — garde `activeElement` du listener global de raccourcis ; `e.preventDefault()` indispensable ici, sinon le navigateur tape quand même le « n » dans le champ qu'on vient de focus) vers `app.openQuickInsert()`, pas vers `openModal()` : un overlay plein écran (`#quickInsertOverlay`, même recette dim+blur que `.modal-overlay` — `rgba(0,0,0,.5)` + `backdrop-filter: blur(8px)`, `z-index:9500`) assombrit tout le reste et centre la barre (`#quickInsertBar`) **de façon absolue** (horizontale ET verticale, via `display:flex;align-items:center;justify-content:center` sur l'overlay — pas un `position:fixed;top:18vh` sur la barre elle-même comme la 1re version). Le champ prend le focus **et démarre la dictée automatiquement** (`autoStartDictation(input)` dans `openQuickInsert()`, champ toujours vierge à l'ouverture — même convention que `openModal()`) ; `attachMic(quickInsertInput)` est posé une fois dans `_initDictation()`, **sans wrapper** (même raison que `#taskTitle` : le hint dépend de `:not(:placeholder-shown) ~` — un sélecteur de fratrie DIRECTE que `{wrap:true}` casserait en insérant le bouton micro dans un `.dictate-field` intermédiaire). Aucune glue supplémentaire nécessaire pour committer la dictée avant lecture : les listeners globaux en phase de capture de `dictation.js` (Enter/Escape/blur) s'exécutent avant les miens (posés sur la cible elle-même, jamais en capture) et écrivent déjà le texte dicté dans `input.value` par le temps que mon code le lit. **Entrée et blur font strictement la même chose** (`confirmQuickInsert()`, sans paramètre) : créer une tâche ponctuelle si un titre a été saisi/dicté (`addTask({title, date: DS(state.navDate), recurrence:'none'}, state.todos)`, datée sur le **jour affiché** — `navDate`, pas forcément aujourd'hui), puis fermer — **pas de rafale** (Entrée referme au lieu de réarmer un nouveau champ, pour ne pas relancer la dictée automatique à chaque tâche et enchaîner les bips Chrome). Échap ou Entrée/blur à vide ferment sans rien créer. Clic sur le backdrop (`onclick="if(event.target===this)closeQuickInsert()"`, même pattern que `reviewModalOverlay`/`adminModalOverlay`) déclenche d'abord un `blur` en cascade (→ `confirmQuickInsert()`), puis son propre appel à `closeQuickInsert()` — un no-op puisque déjà fermé (`overlay.classList.contains('hidden')`). `closeQuickInsert()` appelle `stopDictation()` (même reflexe défensif que `closeModal()`, même si déjà no-op la plupart du temps grâce aux listeners capture ci-dessus) puis vide l'input **avant** son propre `.blur()`. `openQuickInsert()` s'annule silencieusement si une modale (`.modal-overlay:not(.hidden)`) est déjà ouverte. La modale complète (catégorie, récurrence, moment...) reste accessible via le bouton rond `+`/clic droit. Ouverture/fermeture en `transition: opacity` sur l'overlay + `transform: scale/translateY` sur la barre (pas `@keyframes`, pas de `display:none` — `.hidden` retombe juste à `opacity:0; pointer-events:none`, même recette que `.update-toast`) pour que les deux sens soient symétriquement smooth. **Hint (icône + « Nouvelle tâche… ») jamais dans l'attribut `placeholder`** — un texte assez long pour être utile s'y serait fait tronquer par un champ étroit, sans possibilité d'y animer sa disparition ; à la place, `placeholder=" "` (espace, jamais rendu) sur l'input sert uniquement de déclencheur à `:placeholder-shown` en CSS, et le vrai hint est un `<div class="quick-insert-hint">` superposé (`position:absolute;inset:0;right:34px` — la marge de droite laisse la place au bouton micro) qui s'efface en fondu (`.quick-insert-input:not(:placeholder-shown) ~ .quick-insert-hint { opacity:0 }`) dès la 1re frappe/dictée — l'input récupère alors toute sa largeur, sans rien à côté du texte. **Remplace un sous-système `quickAdd`/`qaCloud` mort** retiré à cette occasion — JS présent (`state.quickAddTarget`, `app.quickAdd()`, `renderQACloud()`, SCSS `.qa-cloud`/`.quick-add-bar`/`.quick-add-opt*`) mais son HTML avait disparu d'`index.html`, chaque fonction s'auto-annulait via `if (!el) return`.
- **Inline inputs:** `addCategoryFromView` / `addProjectFromView` inject `<input>` in `.category-card--add` (no `prompt()`)
- **Modal principal (Ajouter/Éditer une tâche) — titre seul toujours visible, tout le reste en sections thématiques dépliables :** un seul écran (plus de mode guidé séparé, retiré — voir plus bas), toujours dans `.modal-main`. Seul le Titre (`#taskTitle`, focus auto + dictée auto sur `openModal()`) reste en permanence à l'écran hors accordéon : départ délibérément minimaliste, demandé par Hugues (avant : la rangée « Quand », les pastilles de priorité et les sous-tâches étaient elles aussi toujours visibles hors accordéon). Tout le reste — Sous-tâches (`#modalSubtaskSection`/`#modalSubtaskList`), Quand (`.schedule-mode-option` + `#dateTimeGroup`), Durée (estimée/réelle, `.duration-row`), Priorité (`.priority-pastille-row`), Notes (`#taskDescription`), Étiquettes (onglets Catégories/Projets/Intentions), Compteur — vit dans `.modal-cat-list` : 7 sections **indépendamment** dépliables (`.modal-cat-section#catSection-{subtasks|when|duration|priority|notes|tags|counter}`, pas un accordéon exclusif — plusieurs peuvent être ouvertes en même temps), chacune une ligne unique au repos (icône SVG trait + libellé + **aperçu de la valeur courante** + chevron, `.modal-cat-header` → `app.toggleCatSection(key)` → `setCatSectionOpen()`/`toggleCatSection()` dans `modal.js`) qui se déplie en `.modal-cat-body` (`grid-template-rows: 0fr→1fr`, même famille que `.subtask-collapse`/`.focus-queue`, jamais `max-height`) — **le padding ne va jamais sur `.modal-cat-body-inner`** (c'est CET élément que la grille écrase à 0, et `overflow:hidden` ne masque que le débordement d'un enfant, jamais le padding de sa propre boîte) mais un cran plus bas sur `.modal-cat-body-pad`, un vrai enfant dont le rendu déborde alors de la boîte à 0 et se fait couper net (bug corrigé : sans ce découplage, le padding restait visible en permanence, laissant transparaître le début du contenu même section repliée). **Aperçu toujours à jour même repliée** (`catPreview-{key}`, ex. « 2/4 » pour Sous-tâches, « Aujourd'hui », « ≈ 30 min », « Haute », « Maison, Projet X », « Désactivé ») : `_refreshCollapsePreviews()`/`_fmtXxxPreview()` (modal.js) recalculent le texte depuis `state`/le DOM (`_fmtSubtasksPreview()` lit `_modalSubtasks`), déclenchés par UN SEUL listener délégué (`click`/`input`/`change` sur `.modal-main`, débouncé via `requestAnimationFrame`) plutôt que filetés dans chaque mutateur (`selectBigMode`, `selectPriority`, toggle de tag…) — robuste à un futur champ ajouté sans y penser. **Repli/dépli automatique piloté par la donnée, pas par « nouveau vs édition »** (`_autoExpandCatSections()`/`_hasCatData(key)`, appelée en fin de `openModal()`, `openEditModal()` et `discardDraft()`) : une section s'ouvre d'elle-même SSI elle contient déjà une valeur non par défaut (récurrence/Inbox/Backlog/heure/moment pour Quand, une durée saisie, une priorité choisie, des notes, au moins un tag, le compteur activé) — sur une tâche neuve tous les champs sont vides, donc tout reste replié (le même appel couvre les deux cas, pas de branche séparée « création » vs « édition ») ; en édition, le contenu existant ne se cache donc jamais derrière un clic, mais une tâche simple (juste une date) reste compacte. **Seule exception : Sous-tâches** (`_hasCatData('subtasks')` renvoie toujours `true`) — reste TOUJOURS dépliée par défaut, y compris une tâche neuve sans aucune sous-tâche, demandé explicitement par Hugues (la chose la plus utilisée juste après le titre) ; dans `openEditModal()`, `populateModalSubtasks(effT.subtasks || [])` est appelée **avant** `_autoExpandCatSections()` (seule section dans ce cas, le reste du formulaire étant déjà peuplé plus tôt) — sinon l'aperçu replié lirait encore `_modalSubtasks` de la tâche précédemment éditée au moment du calcul. Alt+Tab (raccourci vers la durée estimée, voir plus bas) force d'abord l'ouverture de la section Durée (`setCatSectionOpen('duration', true)`) avant de focus — une ligne de grille repliée à 0 resterait sinon techniquement focusable mais invisible. **Mode guidé retiré entièrement** (`openGuidedCards`/`closeGuidedCards`/`guidedNext`/`guidedBack`/`guidedFinish`/`_syncGuidedToMain`/`_buildGuidedSummary`/`#guidedOverlay`/`.guided-*` — tout supprimé) : c'était un assistant à 4 écrans parallèle au formulaire dense, qui dupliquait sa logique (recurrence day-checkboxes recopiés 3× dans le fichier) et cassait par endroits (catégorie/projet du mode guidé ciblaient des `<select>` déjà supprimés du HTML, donc toujours vides ; fermer le modal en mode guidé sans passer par `closeGuidedCards()` — Échap, ou même une sauvegarde réussie via `guidedFinish()` — laissait `.modal-main` coincé en `display:none`, modal vide à la prochaine ouverture). Le flux unique élimine ces classes de bug par construction : une seule surface, un seul chemin de fermeture (`closeModal()`), un seul état à resynchroniser (aucun). Clavier : Entrée sauve et ferme depuis **n'importe quel champ** de `.modal-main` (`modal.js`, listener global `keydown` sur `document` scopé par `main.contains(e.target)`) — Tab garde la navigation par défaut du navigateur ; Option/Alt+Tab saute directement au champ Durée estimée (`.duration-stepper[data-target="taskDurationEstimated"] .dur-display`). Exclusions à ce comportement générique : `TEXTAREA` (notes — Entrée garde son sens de retour à la ligne), `BUTTON`/`A` (Entrée doit activer CE bouton, pas sauver toute la tâche), et tout champ qui gère déjà lui-même Entrée via `e.preventDefault()` (sous-tâche inline, édition de titre de sous-tâche, création inline de catégorie/projet/intention, combobox de titre avec suggestion active — celles-ci doivent explicitement appeler `preventDefault()` sur Entrée pour rester exclues). **Tout nouveau champ ajouté à ce modal doit soit se conformer à ce comportement (Entrée sauve), soit appeler `preventDefault()` s'il a son propre sens pour Entrée.** **Option/Alt+Entrée = sauver PUIS basculer en mode Focus** sur la tâche qui vient d'être créée/éditée (`app.saveTask(true)`, id capturé via `state.editingId || todos[todos.length-1].id` **avant** `closeModal()` qui le remet à `null` ; `focusStartOn(id, ds, null, { fallbackToEdit: false })` — le nouveau 4e paramètre `opts.fallbackToEdit` désactive le repli habituel de `focusStartOn` vers `openEditModal()` quand la cible n'a pas d'occurrence aujourd'hui, pour ne jamais rouvrir le modal qu'on vient de fermer). Même raccourci pour une **sous-tâche** : ajout inline en vue jour (`app.addSubtaskInline`/`confirm(reopen, andFocus)`), dans le modal (`addModalSubtaskInline`, uniquement si `state.editingId` — une sous-tâche ajoutée pendant la création d'une tâche pas encore sauvée n'a pas d'id de tâche réel à cibler, Alt+Entrée s'y comporte alors comme Entrée simple) et depuis le mode Focus lui-même (`app.focusAddSubtask`, bascule le Focus courant sur la sous-tâche tout juste créée) — jamais pour une sous-sous-tâche (`parentStid` défini), le Focus ne ciblant que la profondeur 1 (cf. `focus.js`).
- **Édition `contentEditable` — jamais `esc()` sur `textContent` :** le rendu écrit `${esc(x)}` dans du **HTML** (correct), mais un retour au DOM se fait via `el.textContent = x` **brut** — `textContent` échappe déjà de lui-même, donc `esc()` y écrit `&gt;` comme texte VISIBLE, que la sauvegarde suivante (`el.textContent.trim()`) relit tel quel dans l'état, puis `esc()` au rendu en rajoute une couche : `>` → `&gt;` → `&amp;gt;` → `&amp;amp;gt;`, un cran à chaque cycle. Corrigé dans `editSubtaskTitle()` (app.js) et `editModalSubtask()` (modal.js), sur les chemins « sortie sans changement » et « Échap » des deux. Règle : `esc()` uniquement dans les gabarits de chaîne HTML, jamais dans une affectation à `textContent`/`.value`
- **Undo:** snapshot before each mutation, stack of 50, check `canUndo()`
- **Modal draft:** autosave 300ms debounce in `modalDraft` localStorage key
- **Modal — édition d'une occurrence récurrente = jamais toute la série :** `openEditModal(id, dateStr)` pose `state.editingDate = dateStr` (state.js) en plus de `state.editingId` — c'est CE couple qui détermine, dans `saveTaskLogic()` (modal.js), si les champs de « contenu » (titre, description, priorité, catégories/projets/intentions, heures, moment, durée estimée, sous-tâches) s'écrivent dans `t.overrides[dateStr]` (`perOccurrence = data.recurrence !== 'none' && !!state.editingDate`) plutôt que sur le master `t` — les autres occurrences (passées/futures) ne voient donc jamais l'édition. Les champs qui DÉFINISSENT la récurrence (recurrence/recDays/recMonth/…/startDate), le compteur et `durationReal` restent, eux, toujours sur le master (voir la liste complète dans Data model → `overrides`). Le formulaire lui-même se PEUPLE via `resolveOccurrence(t, dateStr)` (valeurs effectives de cette date), jamais `t` brut, sauf pour les champs justement master-only. Ce même principe (override de l'occurrence affichée, jamais le master) s'applique aussi en dehors du modal : priorité/moment par clic droit (`setPriorityMany`/`setDayPeriodMany` → `_resolveOccurrences()` + `setOccurrenceField()`), glisser-déposer en vue jour qui change le moment ou la priorité (`initDayDragDrop()`), édition en place de la durée estimée (`_editEstimateLabel`), et Focus (`focusSetEstimate` — `ref.t` pour une tâche de premier niveau récurrente passe par `setOccurrenceField(ref.t, DS(today()), …)` ; l'affichage de la tâche courante, `getCurrentFocusTask()`/`toFocusItem()`, résout lui aussi `resolveOccurrence(ref.t, DS(today()))` pour ne jamais montrer une valeur périmée si un override existe déjà pour aujourd'hui).
- **Subtasks (édition tâche existante):** contrairement au reste du formulaire (appliqué seulement au Save), chaque mutation de sous-tâche (`toggleModalSubtask`, `removeModalSubtask`, `addModalSubtask`/`addModalSubtaskInline`, `editModalSubtask`, réordonnancement par glisser-déposer — voir plus bas) persiste immédiatement dans `state.todos` + `saveTodos()` via `_persistSubtasksIfEditing()` (modal.js) — une fermeture Échap ne perd donc jamais de sous-tâches. Pour une tâche RÉCURRENTE éditée avec une occurrence connue (`state.editingDate`, posé par `openEditModal(id, dateStr)`), cette persistance immédiate écrit dans `t.overrides[state.editingDate].subtasks` (cf. calendar.js `occurrenceOverride`) au lieu de `t.subtasks` — voir « édition cette occurrence seulement » dans le tableau des modules. `app.closeModal()` déclenche un `render()` si `consumeModalSubtasksDirty()` renvoie true, pour que la vue en arrière-plan reflète le changement. **Sous-sous-tâches (un niveau de plus, jamais davantage — décision produit)** : chaque fonction ci-dessus accepte un `parentStid` optionnel en dernier argument (résolu via `_findModalSubtask(stid, parentStid)`, modal.js, ou `app._findSubtask(subs, stid, parentStid)` côté vue jour, `subs` = tableau déjà résolu via `occurrenceSubtasks(t, ds)`) — absent = profondeur 1 (`_modalSubtasks`/`t.subtasks`), présent = profondeur 2 (`.subtasks` de ce membre précis). Rendu récursif : `_subtaskRowsHTML(list, parentStid)` (modal.js) ne rappelle elle-même que pour `!parentStid`, ce qui plafonne naturellement la récursion à un cran ; `subtaskListHTML(subtasks, todoId, ds, parentStid)` (render.js, vue jour) suit le même principe. Bouton dédié « + » (`.subtask-add-nested-btn`, modal ; ré-utilise l'icône `.subtask-add-mini` existante, vue jour) n'apparaît QUE sur les lignes de profondeur 1 — une sous-sous-tâche ne peut jamais elle-même avoir d'enfant. La liste imbriquée (`.modal-subtask-nested` / `.subtask-list--nested`, `data-parent-stid` sur le conteneur ET sur chaque ligne enfant) est injectée à la volée au premier ajout (mêmes garde-fous que `ctxAddSubtask` pour le niveau racine — annuler un ajout vide sans rien créer retire le bloc, mais SEULEMENT ce niveau : `list.remove()`, jamais `.closest('.subtask-collapse')` qui couvrirait tout le niveau racine). Conversions tâche⇄groupe (`convertTaskToGroup`/`convertGroupToTask`, voir « Groupement de tâches ») et duplication (`duplicateTodo`/`duplicateMany`/`_insertClone`) préservent ces sous-sous-tâches — `convertGroupToTask` aplatit volontairement un niveau de trop si un membre du groupe en avait déjà (un membre était une tâche autonome, donc `m.subtasks` était déjà SON niveau 1 ; le garder tel quel sous le nouveau parent créerait un 3e niveau interdit). L'avertissement de complétion (`toggleTodo`, « tâche a des sous-tâches non faites ») compte récursivement via `app._countIncompleteSubtasks()`, sinon une sous-sous-tâche non faite serait ignorée silencieusement. **Réordonnancement par glisser-déposer** (`.subtask-drag-handle`, icône grip SVG — remplace d'anciennes flèches ↑/↓ `moveModalSubtask`, retirées) : implémenté à la main via `mousedown`/`mousemove`/`mouseup` (`_onSubtaskListMouseDown`/`_onSubtaskDragMove`/`_onSubtaskDragEnd`, modal.js), **pas** l'API HTML5 `draggable`/`dragover` — `.modal-overlay`/`.modal` ont un `backdrop-filter` sur eux, qui casse silencieusement toute vraie cible de drop native chez un descendant (bug Chromium documenté dans la section CSS/SCSS plus bas, déjà rencontré et contourné pour le modal Bilan) ; le drag manuel n'utilise aucune cible de drop native et n'est donc pas concerné. Listener délégué posé une seule fois sur `#modalSubtaskList` (`el.dataset.dragBound`, persiste à travers les `innerHTML` successifs de `_renderModalSubtasks()`). Zone haut/bas de la ligne survolée (milieu de son `getBoundingClientRect()`) détermine avant/après (`.drop-target-swap.drop-before`/`.drop-after`, même sémantique visuelle que `.subtask-item` en vue jour) — pas de zone centrale d'imbrication ici (déjà couverte par le bouton dédié `.subtask-add-nested-btn`). Liste de comparaison filtrée sur `data-parent-stid` (même valeur, ou absence des deux) : le conteneur DOM est partagé entre les deux profondeurs, donc une ligne de niveau 2 ne peut jamais devenir cible d'un drag de niveau 1 et inversement. `body.subtask-drag-active` (curseur grabbing + `user-select:none`) le temps du drag, pour ne pas sélectionner du texte en survolant les autres lignes
- **Recurrence:** single todo object, not instances — `completedDates[]` tracks done dates
